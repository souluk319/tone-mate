## 0. 제품 계약

### 한 문장

노래 초보자가 음정을 못 맞히는 원인을 듣기·목표음 진입·음 유지·음정 이동으로 나눠 이해하고, 개인 음역의 5분 훈련 뒤 화면 도움 없이 나아졌는지 확인하는 모바일 코치다.

### 해결할 핵심 문제

기존 튜너는 사용자가 지금 높거나 낮다는 사실은 보여주지만 다음을 충분히 설명하지 않는다.

- 두 음의 차이를 못 듣는 것인지
- 들은 음을 목소리로 옮기는 데 실패한 것인지
- 음을 찾은 뒤 유지하지 못하는 것인지
- 단음은 맞지만 음 사이 간격을 좁히거나 넓히는 것인지
- 실시간 선이 사라져도 같은 결과를 낼 수 있는지

### 제품 약속

- 첫 진단을 완료하면 가장 약한 능력 축과 다음 연습을 알 수 있다.
- 모든 발성 과제는 사용자의 편안한 음역 안에서 제시된다.
- 훈련 성과와 무피드백 검증 성과를 분리해 보여준다.
- 측정 신뢰도가 낮으면 점수를 만들지 않고 재측정을 안내한다.
- 원음은 사용자가 명시적으로 저장하지 않는 한 기기를 떠나지 않고 세션 종료 후 폐기된다.

### 제품이 하지 않는 일

- `음치`, 선천성 음치증, 성대 질환, 호흡·공명 문제의 의학적 진단
- 목소리의 매력, 예술성, 장르 적합성 평가
- 최고음 경쟁과 무리한 음역 확장
- 상용곡·원곡 음원·가사 제공
- AI가 센서 데이터에 없는 발성 원인을 추정하는 것

## 1. 사용자와 사용 상황

### 핵심 사용자

- 16세 이상 노래 초보자 또는 취미 보컬
- 노래방·모임·합창에서 음정 불안을 경험한 사람
- 학원 등록 전 기초 상태를 확인하거나 수업 사이에 혼자 연습하려는 사람
- 악보·화성학보다 귀와 목소리의 연결부터 배우려는 사람

### 2차 사용자

- 학생에게 짧은 자가훈련을 배정하려는 보컬 트레이너·음악 교사
- 자기 연습의 객관적 추세를 보고 싶은 중급 취미 보컬

### 초기 제외 사용자

- 음성 질환을 진단·치료하려는 사용자
- 수술 직후 또는 의료인의 관찰이 필요한 사용자
- 전문 성악 테크닉, 벨팅, 극고음 확장을 원하는 사용자
- 보호자 동의·아동 음성 안전 설계가 필요한 16세 미만 사용자

### 핵심 사용 상황

1. 집의 조용한 방에서 첫 진단을 수행한다.
2. 매일 같은 시간에 5분 루틴을 수행한다.
3. 실시간 피드백을 보며 연습한 뒤 화면 없이 다시 부른다.
4. 다음 날 무피드백 유지 결과로 실제 변화를 확인한다.
5. 반복 정체 시 결과 요약을 보컬 코치에게 공유한다.

## 2. 제품 목표와 성공 지표

### 북극성 지표

`주간 유효 무피드백 재검사 완료 수`

단순 앱 실행이나 연속 출석보다, 측정 가능한 상태에서 화면 도움 없이 다시 수행한 횟수를 핵심으로 본다.

### 활성화

사용자는 설치 후 24시간 안에 다음을 모두 완료하면 활성화된 것으로 본다.

- 환경 검사 통과
- 첫 다축 프로필 생성
- 처방된 첫 5분 루틴 완료

### MVP 알파 목표

| 지표 | 목표 | 비고 |
|---|---:|---|
| 온보딩 시작 → 유효 프로필 완료 | 60% 이상 | 마이크 거부 제외 수치도 병기 |
| 첫 프로필 소요시간 중앙값 | 8분 이하 | 재측정 시간 제외 |
| 일일 루틴 소요시간 중앙값 | 4–6분 | 준비 안내 포함 |
| 사용성 테스트에서 결과 의미 이해 | 참가자의 80% 이상 | 자기 말로 설명 가능해야 함 |
| 유효 발성 trial 비율 | 85% 이상 | 지원 환경·기기에서 |
| 무근거 임상 표현 발견 | 0건 | 카피·AI·고객지원 포함 |
| 원음 비동의 네트워크 전송 | 0건 | 프록시·패킷 검사로 확인 |

학습 효과 목표는 파일럿 결과가 생기기 전 마케팅 약속으로 사용하지 않는다. 내부 분석에서는 무피드백 절대 센트 오차, 간격 오차와 다음 날 유지율을 추적한다.

## 3. MVP 범위

### 포함

- 계정 없이 시작
- 한국어 UI, 고정도법·이동도법 설명
- 마이크 권한, 입력 레벨, 소음, 클리핑, 오디오 경로 검사
- 편안한 음역 캘리브레이션
- 높음·낮음·같음 음정 지각 테스트
- 피아노·사람 목소리 기준음의 단음 재현
- 개인 음역으로 배치된 두·세 음 도수 패턴
- 실시간 피치 레인 훈련
- 피드백 획득 → 감쇠 → 회상 단계
- 무피드백 즉시·다음 날 재검사
- 다축 결과, 측정 신뢰도, 다음 훈련 처방
- 기기 내 진행 기록과 데이터 삭제
- 안전 체크와 세션 중단
- 접근성 기본 지원

### 제외

- 상용곡, 원곡, 반주, 가사 카탈로그
- 사용자가 올린 곡의 보컬 분리·자동 채보
- 소셜 피드, 공개 랭킹, 오디션
- 코치 마켓플레이스와 결제
- 공명·호흡·jitter·shimmer·HNR 기반 건강 판정
- 클라우드 원음 분석
- LLM 실시간 발성 코치
- 전문 발성법, 벨팅, 음역 확장 커리큘럼

### MVP 이후

- 주간 멜로디 전이 과제
- 코치 공유 리포트와 과제 코드
- 선택적 계정·동기화
- 자체 또는 정식 라이선스 곡
- 근거가 제한된 AI 회고·동기 지원
- 셀프 보이스 기준음 실험 기능

## 4. 핵심 개념

| 용어 | 정의 |
|---|---|
| 목표음 | 해당 trial에서 사용자가 내야 하는 기준 주파수 |
| 도수 | 조성 안에서의 상대 위치. 도=1, 레=2, 미=3 등 |
| 편안한 음역 | 통증·압박 없이 두 번 이상 안정적으로 재현한 범위. 낼 수 있는 극단 음역과 다름 |
| 유효 프레임 | 음성·신호·클리핑 조건을 통과한 f0 관측 프레임 |
| 안정 구간 | 시작 탐색과 끝 감쇠를 제외하고 충분한 유효 프레임이 연속된 구간 |
| 획득 단계 | 현재 음과 목표선을 실시간 표시하는 훈련 |
| 감쇠 단계 | 피치 표시를 간헐적·지연 방식으로 줄이는 훈련 |
| 회상 단계 | 기준음을 들은 뒤 실시간 표시 없이 부르는 훈련 |
| 전이 | 연습하지 않은 기준음·음정·멜로디에 같은 능력을 적용하는 것 |
| 측정 신뢰도 | 소음, 음성 검출, 유효 프레임, 클리핑 등을 종합한 결과 사용 가능성 |
| 프로필 | 듣기·진입·정확도·안정도·이동·타이밍의 개별 결과 |

## 5. 전체 사용자 흐름

```text
첫 실행
  → 제품·비의료 범위 안내
  → 마이크 권한
  → 환경 검사
  → 안전 상태 확인
  → 편안한 음역 캘리브레이션
  → 지각 테스트
  → 단음 재현
  → 간격·윤곽 재현
  → 프로필과 측정 신뢰도
  → 오늘의 5분 루틴
  → 획득 훈련
  → 피드백 감쇠
  → 무피드백 회상
  → 세션 요약
  → 다음 날 유지 검사
```

### 중단·복구 흐름

- 마이크 거부: 지각 데모만 허용하고 발성 프로필은 만들지 않는다.
- 소음 실패: 조용한 장소·이어폰 안내 후 다시 검사한다.
- 입력 없음: 마이크 경로·권한·다른 앱 사용 여부를 점검한다.
- Bluetooth 입력 부적합: 기기 마이크 또는 유선 입력을 안내한다.
- 통증·쉰 목소리 응답: 발성 세션을 열지 않고 안전 안내를 제공한다.
- 앱 중단·전화 수신: 현재 trial은 무효 처리하고 재개 시 환경을 다시 확인한다.
- 반복 측정 실패: 점수를 만들지 않고 실패 원인과 지원 링크를 제공한다.

## 7. 기능 요구사항

### 7.1 온보딩·권한

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| ONB-01 | 계정 없이 첫 진단을 시작할 수 있어야 한다. | 네트워크가 없어도 S01–S13 완료 |
| ONB-02 | 앱은 첫 마이크 요청 전에 사용 이유와 원음 기본 비저장을 설명해야 한다. | 시스템 권한 창보다 먼저 설명 노출 |
| ONB-03 | 의료 진단·치료 도구가 아님을 평이한 한국어로 알려야 한다. | 최초 1회와 설정에서 재확인 가능 |
| ONB-04 | 사용자가 거부한 마이크 권한을 반복 팝업으로 강요하지 않는다. | 지각 데모 또는 설정 이동 제공 |

### 7.2 환경 검사

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| ENV-01 | 실제 입력 sample rate·channel·route를 확인한다. | 사용할 수 없는 형식에서 trial 시작 금지 |
| ENV-02 | 2초 주변 소음으로 noise floor를 측정한다. | 초기 기준 미달 시 재측정 안내 |
| ENV-03 | 2초 말하기·허밍으로 입력 레벨과 clipping을 검사한다. | 너무 작음·적정·너무 큼을 구분 |
| ENV-04 | 오디오 경로 변경과 interruption을 감지한다. | 현재 trial 무효화 후 환경 재확인 |
| ENV-05 | Bluetooth 입력이 검증 범위 밖이면 명시적으로 제한한다. | 잘못된 점수 대신 경로 교체 안내 |

### 7.3 안전 상태·음역

| ID | 요구사항 | 수용 기준 |
|---|---|---|

## 9. 신호와 점수 명세

### 9.1 입력 계약

분석 코어는 시간순 PCM mono frame을 받아 다음 관측을 낸다.

```text
PitchObservation {
  timestamp_ms
  f0_hz
  voicing_confidence
  rms_dbfs
  clipped
}
```

원시 PCM은 분석 코어 밖으로 복사하지 않는 것을 원칙으로 한다. UI에는 초당 최대 20개의 요약 관측만 전달한다.

### 9.2 유효성 초기 운영값

- 실제 sample rate와 channel이 0 또는 미지원이면 시작 금지
- clipping frame 비율 2% 초과 시 trial 무효
- 추정 noise floor 대비 신호가 10dB 미만이면 trial 무효 후보
- voicing confidence 0.80 미만 프레임 제외
- 전체 응답 구간에서 유효 프레임 60% 미만이면 점수 미생성
- 안정 구간 600ms 미만이면 `음 유지 부족` 또는 재측정

이 값은 알고리즘별 confidence 의미가 다르므로 기술검증 후 알고리즘별 설정으로 분리한다.

### 9.3 센트

```text
cent_error(t) = 1200 × log2(f0(t) / target_hz)
```

- 음수가 목표보다 낮음, 양수가 목표보다 높음이다.
- 옥타브 오류를 숨기기 위해 modulo 1200으로 접지 않는다.
- 사용자 표준 튜닝은 기본 A4=440Hz이며 설정에서 바꿀 수 있게 설계하되 MVP UI에는 노출하지 않아도 된다.

### 9.4 구간화

- `voice_onset`: 첫 120ms 연속 유효 프레임의 시작
- `target_acquired`: ±50c 안에 250ms 연속 진입한 첫 시점
- `stable_start`: target_acquired 뒤 100ms
- `stable_end`: 음성 종료 150ms 전
- target을 획득하지 못해도 가장 긴 유효 구간의 원시 값을 보존하되 `미획득`으로 표시

시작 글라이드는 진입 지표에 포함하고 안정 정확도에서는 제외한다.

### 9.5 원시 지표

| 필드 | 산식·정의 |
|---|---|
| `center_error_cents` | 안정 구간 cent error 중앙값. signed |
| `absolute_error_cents` | 안정 구간 cent error 절댓값의 중앙값 |
| `stability_cents` | cent error의 scaled MAD = 1.4826×MAD |
| `acquisition_ms` | voice_onset부터 target_acquired까지. 미획득은 null |
| `valid_coverage` | 유효 프레임/전체 응답 프레임 |
| `octave_error` | 중앙 f0가 target의 ±1200c 부근이고 ±100c 밖인 경우 |
| `interval_error_cents` | 실제 두 음 중앙값 차이 − 목표 간격 |
| `contour_correct` | 상행·하행·반복 방향 일치 여부 |
| `onset_error_ms` | 목표 박 대비 voice_onset 차이 |
| `duration_error_ms` | 실제 안정 발성 길이 − 목표 길이 |

### 9.6 정규화 점수 초기값

```text
linear_score(x, good, bad) =
  100                         if x <= good
  100 × (bad - x)/(bad-good) if good < x < bad
  0                           if x >= bad
```

| 축 | x | good | bad |
|---|---|---:|---:|
| 정확도 | absolute_error_cents | 25c | 100c |
| 안정도 | stability_cents | 15c | 60c |
| 목표음 진입 | acquisition_ms | 600ms | 2500ms |
| 음정 이동 | abs(interval_error_cents) | 25c | 100c |
| 타이밍 | abs(onset_error_ms) | 100ms | 500ms |

- 점수는 여러 유효 trial의 중앙값을 사용한다.
- 지각 점수는 전체 정답률과 50/100/200c 구간별 정답률을 함께 표시한다.
- 윤곽은 방향 일치율로 표시한다.
- 초기 경계는 feature configuration으로 버전 관리한다.
- 점수 버전이 바뀌면 과거 원시 지표를 유지하고 표시 점수만 새 버전으로 재계산할 수 있어야 한다.

### 9.7 측정 신뢰도

```text
confidence_score =
  0.40 × valid_coverage_component
  + 0.25 × signal_to_noise_component
  + 0.20 × voicing_component
  + 0.15 × non_clipping_component
```

- 0.80 이상: 높음
- 0.60–0.79: 보통, 제한 문구와 함께 표시
- 0.60 미만: 결과 해석 금지, 재측정

각 component의 변환식은 기술검증에서 고정한다. confidence는 사용자의 능력 점수가 아니다.

### 9.8 피드백 의존도

```text
feedback_dependency = max(0, guided_composite - unguided_composite)
```

- 동일 target·유사 trial 쌍만 비교한다.
- 최소 3쌍 전에는 수치 대신 `데이터를 모으는 중`을 표시한다.
- 높은 값은 실패 판정이 아니라 무피드백 회상 비중을 늘리는 처방 신호다.

## 10. 프로필·처방 규칙

한 사람에게 여러 유형이 동시에 나타날 수 있다. `환경 재측정`은 언제나 능력 해석보다 우선한다.

| 우선 규칙 | 조건 초기값 | 기본 처방 |
|---|---|---|
| 환경 재측정 | confidence <0.60 또는 유효 trial <70% | 환경·경로 다시 확인 |
| 듣기부터 | ≥100c 지각 정답률 <70% | 200→100c 높낮이 구별 |
| 목표음 찾기부터 | 지각 ≥80%, 진입 점수 <60 | 한 음 듣고 찾기, 방향 힌트 |
| 음 유지부터 | 정확도 ≥60, 안정도 <60 | 편안한 음 1–2초 유지 |
| 음 사이 이동부터 | 단음 정확도 ≥70, 이동 <60 | 도–레, 도–미 간격 |
| 리듬과 함께 | 피치 축 ≥70, 타이밍 <60 | count-in과 시작점 연습 |
| 균형 루틴 | 모든 신뢰 축 ≥60 | 혼합 루틴과 주간 전이 |

- 조건에 둘 이상 해당하면 신뢰 가능한 최저 점수를 1순위, 두 번째를 보조 20%로 배치한다.
- 동일 축이 3회 연속 80 이상이면 다음 난이도로 이동한다.
- 동일 축이 3회 연속 40 미만이면 난이도를 낮추고 환경·지시 이해를 먼저 확인한다.
- 2주 이상 유효 훈련에도 변화가 없으면 자동 설명을 강화하지 않고 코치 공유 기능을 제안한다.

## 11. 음정·도수 배치 규칙

### 기본 원칙

- 교육 표시는 `도–레–미`와 `1–2–3`을 우선한다.
- 내부 target은 사용자의 편안한 음역 안에서 가장 가까운 장조 도수 패턴으로 생성한다.
- C 음에서 안전한 한 옥타브가 확보되면 C3/C4/C5의 C 메이저를 사용한다.
- C 메이저 전체가 편안한 음역에 들어오지 않으면 같은 상대 패턴을 다른 조로 전조하고 `이동도법 도`임을 설명한다.
- target은 음역 가장자리보다 최소 2반음 안쪽에 둔다.

### 난이도

| 단계 | 콘텐츠 |
|---|---|
| L0 | 같은 음 찾기, 1초 유지 |
| L1 | 도–레, 레–도, 2초 유지 |
| L2 | 도–미, 미–도, 도–레–도 |
| L3 | 도–솔, 도–미–솔, 솔–미–도 |
| L4 | 5음 상·하행, 속도 변화 |
| L5 | 8음 장음계, 간단한 리듬 |

MVP의 자동 처방은 L0–L3까지만 사용한다. L4–L5는 수동 선택 또는 후속 범위다.

- 사용자가 저장한 원음은 앱 전용 보호 영역에 두고 OS 백업 포함 여부를 명확히 결정한다. MVP 기본은 백업 제외다.
- 모든 삭제는 DB 행, 원음 파일, 캐시와 파생 썸네일까지 포함한다.

## 18. 시스템 구조 결정

### 목표 구조

```text
Flutter UI / 세션 상태 / 로컬 데이터
        │ control + summary observations
        ├──────── Platform plugin ────────┐
        │                                 │
 iOS AVAudioEngine                 Android native audio
        │                                 │
        └────── shared pitch_core ────────┘
                 C/C++ ABI
              YIN baseline + gates
```

- Flutter는 화면·내비게이션·세션 상태·로컬 데이터·콘텐츠 생성기를 담당한다.
- Swift·Kotlin 계층은 권한, 오디오 세션, 입력 경로, interruption과 PCM 수집을 담당한다.
- 연속 PCM을 Dart 메시지로 보내지 않는다.
- 공유 DSP가 기술 게이트를 통과하면 C ABI와 Dart FFI로 연결한다. 제어 호출은 platform channel을 사용할 수 있다.
- 최종 알고리즘은 YIN, pYIN, 경량 CREPE 비교 후 결정하되 MVP에는 최소 하나의 결정론적 온디바이스 경로가 있어야 한다.
- 서버는 MVP 핵심 경로에 필요하지 않다.

### 제품 저장소와 패키지 경계

제품은 ChainShield 소스 저장소와 분리한 `tonemate` 모노레포에서 개발한다. 제품 코드와 #1470 증적은 같은 고정 commit을 가리키지만, 판정과 이슈 수명주기는 분리한다.

```text
tonemate/
  AGENTS.md                        전체 제품 저장소 작업 규칙
  DESIGN.md                        현재 제품·시스템 아키텍처 정본
  apps/tonemate/                  실제 Flutter iOS·Android 앱
  packages/pitch_core/            공유 C++ 음정 분석 코어·Conan recipe
  packages/apple_audio/           AVAudioEngine 연결 Swift package
  packages/tonemate_pitch/        앱이 소비하는 Flutter plugin·Pub package
  distribution/cocoapods/         같은 iOS 코드의 CocoaPods 호환 배포
  bench/                           DSP corpus·benchmark
  docs/specs/                      승인된 제품·기술·#1470 명세
  docs/adr/                        주요 아키텍처 변경 기록
  qa/chainshield/
    AGENTS.md                      #1470 증적 하위 범위 규칙
    ...                            #1470 결합 실행·증적 하네스
```

| 제품 모듈 | 정식 좌표 초기안 | 제품 역할 | ChainShield 실사용 역할 |
|---|---|---|---|
| `pitch_core` | `tonemate-pitch-core/0.1.0@tonemate/stable` | iOS·Android 공유 DSP | Conan Hosted·Group 소비 |
| `apple_audio` | `tonemate.apple-audio@0.1.0` | iOS 오디오 세션·입력 | Swift Registry Hosted·Group 소비 |
| `ToneMatePitch` | `ToneMatePitch@0.1.0` | SwiftPM 미사용 환경의 iOS 호환 배포 | CocoaPods Hosted·Group 소비 |
| `tonemate_pitch` | `tonemate_pitch@0.1.0` | Flutter에 노출하는 제어·관측 API | Pub Hosted·Group에서 실제 앱 build |

좌표와 첫 배포 버전은 저장소 생성 시 확정하되, 한 번 게시한 버전은 같은 바이트에만 결속한다. 배포 산출물은 모노레포의 같은 코드를 패키징하며 포맷별 구현을 복제하지 않는다.

`AGENTS.md`는 코드 없이 편의상 생성하는 일반 안내가 아니라, 이 제품의 실제 작업 경계·검증·보안 규칙을 강제하는 프로젝트 한정 문서다. `DESIGN.md`는 여기의 제품 요구사항을 복사하는 문서가 아니라, 모듈 경계·데이터 흐름·실시간 제약·패키지 build lane의 현재 설계 정본이다. 두 문서는 Phase 0에 코드와 함께 생성하고 구조 변경과 같은 commit에서 갱신한다.

### 패키지 관리 원칙

- Dart·Flutter: `pubspec.lock` 필수. 앱의 정식 manifest는 `tonemate_pitch` 버전 범위를 선언하고, 일반 개발에서만 workspace가 로컬 패키지를 해석할 수 있다.
- iOS 네이티브 의존성: `Package.resolved`를 갖는 SwiftPM을 주 경로로 사용한다.
- CocoaPods: `Podfile.lock`을 갖는 지원 대상 호환 경로로 유지하고, 같은 고정 commit의 iOS 산출물을 사용한다.
- Android: Gradle version catalog·dependency locking, NDK 버전 고정
- C/C++: `conan.lock`과 profile을 버전 관리한다. 외부 DSP 의존성은 제품 필요가 검증된 경우에만 추가한다.
- 각 생태계를 테스트하려고 불필요한 의존성을 넣지 않는다.
- #1470 증적에서 workspace, `path`, `git` 의존성 또는 이전 cache로 로컬 소스를 해석한 결과는 ChainShield 소비로 인정하지 않는다.
- Proxy 검증을 위해 제품에 외부 의존성을 임의로 추가하지 않는다. 실제 고정 commit에 해당 포맷의 외부 좌표가 없으면 그 조합은 사유와 함께 `N/A`로 판정한다.

Flutter 공식 문서는 네이티브 고빈도 호출에 [Dart FFI](https://docs.flutter.dev/platform-integration/bind-native-code)를 제공하고, 현재 [SwiftPM 통합](https://docs.flutter.dev/packages-and-plugins/swift-package-manager)을 iOS 네이티브 의존성의 기본 방향으로 안내한다. iOS 입력은 [AVAudioEngine inputNode](https://developer.apple.com/documentation/avfaudio/avaudioengine/inputnode), Android 저지연 경로는 [Oboe/AAudio 지침](https://developer.android.com/games/sdk/oboe/low-latency-audio)을 기준으로 검증한다.

## 20. 출시 게이트

MVP 알파는 다음을 모두 만족해야 한다.

1. 기술검증 계획의 필수 T-gate가 iOS와 Android에서 PASS다.
2. 8–12명 사용성 테스트에서 80% 이상이 다축 프로필과 다음 행동을 자기 말로 설명한다.
3. 지원 기기에서 유효 trial 비율 85% 이상이다.
4. 낮은 신뢰도 샘플에서 점수 억제가 동작한다.
5. guided·unguided·retention 결과가 분리 저장되고 UI에서 혼동되지 않는다.
6. 안전 중단 5개 시나리오가 모두 통과한다.
7. 비동의 원음 저장·전송이 0건이다.
8. 직접·전이 의존성, lockfile, 라이선스와 자산 권리 manifest가 완성된다.
9. `음치 진단`, 치료, 성대 상태 추정 등 금지 카피가 0건이다.
10. 알려진 제한과 지원하지 않는 오디오 경로가 릴리스 노트에 명시된다.
11. AC-07의 clean package build가 재현되고 dependency manifest·lockfile·archive digest가 일치한다.

ChainShield #1470 판정은 이 제품 출시 게이트와 증적을 공유하지만 독립적으로 기록한다. 같은 제품 commit이 일반 원격에서 재현되고 ChainShield에서만 실패하면 #1470 또는 파생 ChainShield 결함으로 분류한다. 반대로 양쪽에서 실패하면 제품 또는 패키징 결함으로 분류한다.

- 온디바이스·무계정·원음 비저장을 기본값으로 한다.
- 단일 음치 점수를 만들지 않는다.
- C 메이저 도수 체계를 중심에 두되 안전을 위해 전조를 허용한다.
- 상용곡과 AI 발성 진단은 MVP에서 제외한다.
- 제품은 독립 `tonemate` 모노레포에서 개발하고 #1470은 고정 commit의 소비·증적만 관리한다.
- Pub은 `tonemate_pitch` 실제 Flutter plugin 배포·소비 경로이므로 #1470 범위에 포함한다.
- SwiftPM을 주 경로, CocoaPods를 지원하는 호환 경로로 유지하되 같은 iOS 소스와 제품 commit을 사용한다.

### 기술검증에서 결정

- YIN, pYIN, 경량 CREPE 중 MVP 기본 피치 추정기
- 공유 C++ DSP와 플랫폼별 구현의 최종 경계
- 알고리즘별 voicing confidence 기준
- 센트·SNR·지연·배터리 운영값
- Bluetooth·USB 오디오의 지원 범위
- opt-in 원음 저장 암호화와 OS 백업 정책

### 사용자 검증에서 결정

- 무료·유료 경계
